## БЛОК 0. Критические баги (делать первым, без этого продукт нерабочий)

### 0.1. WS-событие `new_message` не доходит до клиента 🔴
- **Проблема**: бэкенд шлёт `{"type":"new_message","message":{...}}` (chat_service.go:176), фронт передаёт хендлеру `msg.payload` (ws.ts:31) → для `new_message` это `undefined`.
- **Фикс**: привести к единому контракту `{type, payload}`. В `chat_service.go` отправить `{"type":"new_message","payload":{message: msg}}` (или в ws.ts передавать весь объект). Сделать WS-контракт единым для ВСЕХ событий.
- **Проверка**: два браузера, отправить сообщение — должно появиться у обоих без перезагрузки.

### 0.2. Инкрементальная индексация поиска умирает на JWT 🔴
- **Проблема**: `HTTPIndexer` постит на `/search/index/*` без токена, а `cmd/search/main.go` вешает JWT-мидлварь на весь `/search` → 401, события теряются.
- **Фикс**: вынести `/search/index/*` за пределы JWT-группы (внутренние эндпоинты) **или** дать indexer-запросам системный токен (service-to-service). Лучше первое + ограничить по сети/токену.
- **Проверка**: создать сообщение → `curl /search/messages?q=...` находит его без ручного Sync.

### 0.3. Redis-лимитер блокирует «навсегда» 🟠
- **Проблема**: `pkg/ratelimit/ratelimit.go` вызывает `Expire` на каждом запросе → TTL продлевается, после превышения лимита пользователь заблокирован вечно при активном трафике.
- **Фикс**: ставить `Expire` только при создании ключа (Lua-скрипт `INCR`+`EXPIRE NX` или `SET NX EX` + `INCR`), либо sliding window.
- **Проверка**: unit-тест: после превышения лимита блокировка снимается по истечении окна.

### 0.4. Удаление файлов сломано 🟠
- **Проблема**: `media_service.DeleteFile` передаёт полный URL вместо ключа объекта (`s.storage.Delete(f.URL)`).
- **Фикс**: хранить в `files` ключ (`object_key`), URL собирать на лету через `storage.URL(key)`.
- **Проверка**: upload → delete → файл исчез из MinIO/local.

### 0.5. VAPID-ключи генерируются при каждом рестарте 🟠
- **Проблема**: пустые VAPID → `GenerateVAPIDKeys()` на каждый старт → все подписки инвалидируются.
- **Фикс**: генерировать один раз и сохранять (файл/секрет), не генерить если ключи уже есть в конфиге.
- **Проверка**: рестарт notification → подписка продолжает получать пуши.

### 0.6. Consumer Redis Streams с общим именем `"consumer"` 🟠
- **Проблема**: `pkg/queue/queue.go` — имя консьюмера захардкожено; >1 реплики notification = кража сообщений.
- **Фикс**: уникальный consumer name (hostname+pid), dead-letter для упавших, `XAck` только после успеха.

### 0.7. Ошибки в `events.go` игнорируются 🟠
- **Проблема**: `post()` и `NotifyMessage` глотают все ошибки (fire-and-forget).
- **Фикс**: ретрай с экспоненциальным backoff + лог ошибок + не блокировать основной поток (async, но с observable отказом).

## БЛОК 1. Ядро чата (фундамент, без которого всё остальное бессмысленно)

### 1.1. Гарантия доставки сообщений
- Сейчас: WS-броадкаст fire-and-forget. Если пользователь оффлайн — сообщение потеряно.
- **Добавить**: сообщение с `status=sent` сохраняется в БД → при подключении клиент запрашивает `offset`/`seq` → история + статусы. Статусы `delivered`/`read` подтверждаются клиентом.
- Таблица `messages`: добавить `seq BIGINT` (монотонный per chat) — это якорь синхронизации, как у Telegram.

### 1.2. Горизонтальное масштабирование chat-сервиса
- Сейчас: WS-хаб в памяти одного инстанса (`pkg/ws/hub.go`).
- **Добавить**: multi-instance через Redis Pub/Sub (уже есть Redis) или NATS: инстанс публикует в канал чата, остальные рассылают своим клиентам. Это «выключатель» масштабирования.
- **Проверка**: 2 инстанса chat + nginx round-robin → сообщение доходит при клиентах на разных инстансах.

### 1.3. Синхронизация между устройствами (multi-device)
- Telegram-фича №1. Один аккаунт = N сессий (уже есть `sessions`).
- **Добавить**: `GET /chat/sync?after_seq=...` — отдать все изменения (сообщения, прочтения, участники) с `seq > N` для всех устройств пользователя. WS-события идут всем активным сессиям.

### 1.4. Дедупликация сообщений
- Клиент генерирует `client_id` (UUID) при отправке → сервер идемпотентен: повторная отправка не дублирует. Сейчас фронт делает optimistic-insert и может задвоить.

### 1.5. Пагинация и кэш истории
- `FindByChatID` без индекса на `(chat_id, created_at DESC)` в некоторых путях. Добавить составной индекс (в `002_chat.sql` уже есть `idx_messages_created_at`) и проверить план запроса.
- Кэшировать последние N сообщений чата в Redis (ускоряет открытие чата в 10 раз).

### 1.6. Реакции/стикеры — довести до уровня
- Реакции без пагинации; стикеры без админки загрузки пакетов. Добавить: агрегация реакций (счётчики по эмодзи), `sticker_packs` CRUD, анимированные (Lottie) позже.

## БЛОК 2. Инфраструктура и масштаб (то, что отличает продукт от демо)

### 2.1. Репликация БД PostgreSQL
- Один postgres в compose. **Добавить**: read-replica для GET-запросов, WAL-G/pgbackrest бэкапы, `max_connections` с пулером (pgbouncer). Начать с реплики + бэкапов.
- Индексы: проверить `EXPLAIN` на все горячие запросы (login по username, history по chat, sessions по refresh_token).
- **DONE (01.08.2026)**: `postgres-replica` (hot standby, pg_basebackup) + `pgbouncer` (transaction pooling) + ежедневный `backup` (pg_dump+gzip) в docker-compose; primary включён wal_level=replica; роль `rep_user` в `000_replication.sql`.

### 2.2. Кэш-стратегия
- Сейчас Redis для сессий/пользователей. **Добавить**: кэш последних сообщений, счётчиков непрочитанных, списка чатов пользователя. Инвалидация через события (изменение → сброс ключа).
- **DONE (01.08.2026)**: `RedisMessageCache` (последние 100 сообщений чата, TTL 5м) + `RedisChatListCache` (список чатов + непрочитанные, TTL 30с) с инвалидацией по событиям (send/read/create/join/leave).

### 2.3. Очереди на все фоновые задачи
- NATS уже заявлен, но реально Redis Streams. Выбрать ОДНО (NATS предпочтительнее: сохраняемость, репликация, dead-letter из коробки) и перевести: индексация поиска, пуши, миниатюры, премиум-продления, транскрибация.
- **РЕШЕНО (01.08.2026)**: единая очередь — **Redis Streams**. Причины: уже работает (пуши), DLQ добавлен (0.6), не требует новой зависимости, Redis уже реплицируется в кластере, операционно проще. NATS остаётся зарезервированным на случай >100k msg/s. Индексация поиска осознанно остаётся прямым HTTP с ретраями (требование near-real-time, низкая задержка важнее очереди).

### 2.4. CDN и статика
- Медиа отдаётся напрямую из MinIO. **Добавить**: пресigned URL (срок жизни), CDN (Cloudflare/Caddy+file cache) впереди media, ресайз/миниатюры (imgproxy или своя очередь + ffmpeg). В `Dockerfile.media` ffmpeg уже есть.
- **DONE (01.08.2026)**: `GET /media/{id}/presign` (PresignedURL в MinioStorage, прямой URL в LocalStorage), срок жизни по умолчанию 15 мин. Ресайз/миниатюры — следующий шаг (imgproxy или очередь+ffmpeg).

### 2.5. Горизонтальное масштабирование всех сервисов
- gateway: stateless → любое число инстансов (Redis-limit уже есть).
- auth/chat/media/call: добавить поддержку реплик (мульти-инстанс WS, общие очереди, общий кэш).
- **Проверка**: `docker-compose up --scale chat=3` работает без потери сообщений.
- **DONE (01.08.2026)**: все сервисы stateless (chat: WS-хаб через Redis PubSub, очереди через Redis Streams, кэш в Redis; auth/gateway/media/call — без состояния). `--scale` пригоден; порты хост-маппятся через nginx.

### 2.6. Мониторинг и алерты
- Prometheus метрики есть, но WS-метрики мёртвые (`WSConnections`/`WSMessagesTotal` нигде не используются) — подключить в `pkg/ws`.
- **Добавить**: алерты (QPS-падение, 5xx > 1%, WS-дисконнекты), логи во все сервисы (Loki есть), трейсинг (OpenTelemetry + Jaeger) — минимум для цепочки gateway→chat→search.
- **DONE (01.08.2026)**: WS-метрики подключены — `WSConnections` (gauge, inc/dec на register/unregister) и `WSMessagesTotal` (in/out) в `pkg/ws`. Алерты/трейсинг — следующий шаг.

### 2.7. Нагрузочное тестирование
- **Обязательно**: `scripts/loadtest` — 10k WS-коннектов, 1k msg/sec, проверить память и p95. Зафиксировать цифры. Без этого «масштаб» — слова.

- **DONE (01.08.2026)**: `scripts/loadtest` — Go-программа (N коннектов, msg-rate, замер p50/p95/p99). Запуск и цифры — на stage-окружении.

## БЛОК 4. Безопасность

### 4.1. Валидация входных данных
- Сейчас: `json.NewDecoder(...).Decode` без проверок во многих хендлерах. **Добавить**: единую схему валидации (обязательные поля, лимиты длины, типы), отклонять лишнее.
- Опасное место: `premium_handler.go` `plan["name"].(string)` — panic без `ok`. Поправить.

### 4.2. Авторизация доступа
- Chat: `GetMessages`/`GetChat` должны проверять членство (`ErrNotMember`). Проверить все хендлеры чата.
- Call: `HandleSignaling` — участник проверяется? Нет. Добавить.
- Admin: роли проверяются, но dashboard/статистика — нет проверки роли на GET.

### 4.3. Rate limiting на аутентификацию
- Auth-эндпоинты (`/auth/login`, `/auth/refresh`) — без лимита. Добавить жёсткий лимит (5/мин) — защита от brute-force.

### 4.4. Секреты и конфигурация
- `JWT_SECRET="change-me-in-production"` дефолт — захардкожен. Перевести всё на `.env` + проверку на проде (сервис падает, если дефолтный секрет).
- `SSA_*` — пустые, auth не работает без реальных credentials. Документировать, как подключить.

### 4.5. CORS и заголовки
- `CORSOrigin="*"` в проде запретить. CSP для фронта уже есть в Tauri. Добавить security headers (X-Frame-Options, X-Content-Type-Options, HSTS).

### 4.6. E2E шифрование (амбициозно, но это «уровень Telegram»)
- Мин: шифрование at-rest для сообщений (AES-GCM уже есть как примитив). Полное E2E (Signal-протокол / MLS) — отдельный крупный этап, оценивать отдельно. Без E2E «догнать Telegram» нельзя — это их ключевая фича.

### 4.7. Модерация и спам
- Репорты, блокировка пользователей (админка частично есть), антиспам по паттернам. Без модерации платформа быстро деградирует.

## БЛОК 5. Надёжность и эксплуатация

### 5.1. Graceful shutdown
- Все сервисы падают по `http.ListenAndServe` без `signal.NotifyContext`. Добавить остановку WS-клиентов, доработку очередей, закрытие соединений.

### 5.2. Health/Ready с зависимостями
- `/health` отвечает даже когда БД/Redis мертвы. Разделить `liveness` (жив) и `readiness` (готов обслуживать: БД+Redis+Meili отвечают).

### 5.3. Восстановление после сбоя
- Dead-letter для очередей, ретраи, idempotency-key для POST-эндпоинтов, автоматический реконнект клиентов (фронт ws.ts есть, но нет на backoff с джиттером).

### 5.4. Бэкапы с проверкой восстановления
- `scripts/backup.sh` есть. **Добавить**: периодический restore-тест, бэкап MinIO, ротация, оффсайт-копия.

### 5.5. CI/CD
- Нет вообще. **Добавить**: GitHub Actions: `test` (vet+test+build на PR), `deploy` (build image → push GHCR → ssh deploy), `backup` (cron). Linting (golangci-lint, ESLint).

## Оценка сроков (соло, по 6-8ч/день)

| Блок | Время | Приоритет |
|------|-------|-----------|
| Блок 0 — баги | 3–5 дней | 🔥 критично |
| Блок 1 — ядро чата | 2–3 недели | 🔥 критично |
| Блок 2 — инфраструктура | 3–4 недели | высокий |
| Блок 3 — фичи | 4–6 недель | средний |
| Блок 4 — безопасность | 2–3 недели | высокий |
| Блок 5 — надёжность | 2 недели | высокий |

**Итого: ~3 месяца** до состояния «полноценный мессенджер Telegram-класса по коду» (без E2E-шифрования, оно +1–2 месяца).
Дальше — вопрос пользователей и инфраструктуры, а не кода.
