# Haze Messenger — Задача работнику: Production-Ready MVP

## Контекст

Проект `haze/` — мессенджер на Go (бэкенд, 9 микросервисов) + Vue (веб) + Tauri 2 (десктоп). Сейчас это рабочий прототип: сервисы подняты, но есть критические баги, заглушки и отсутствует инфраструктура.

**Задача**: превратить прототип в production-ready MVP, способный выдержать десятки тысяч пользователей и стать базой для дальнейшего роста. Приоритет — **качество и архитектура**, а не количество фич.

## Правила работы

1. Работай итерациями. Каждую итерацию: фикс → тесты → `go test ./...` + `go vet ./...` + `npm run build` → коммит в github.com/cotton-msg.
2. После каждого этапа запускай `scripts/test.sh` и покажи результат заказчику.
3. Не добавляй зависимостей без необходимости.
4. Весь новый код — на английском, комментарии на русском (по необходимости).
5. Никаких секретов/ключей в коде — всё через env vars.

## ЭТАП 1: Критические фиксы (сделать в первую очередь)

1. **Админ-панель `ChangeRole` сломана** — `internal/handler/app_handler.go:238` вызывает `userRepo.UpdateUsername()` вместо смены роли.
   - Добавь `UpdateRole(userID, role)` в `user_repo.go`
   - Почини хендлер, добавь валидацию ролей (owner > admin > moderator > user)
2. **Порядок сообщений во фронте** — `chatStore.sendMessage` использует `unshift()`, а история приходит хронологически. Сообщения ломаются по порядку.
   - Определись с контрактом API (например `messages` всегда DESC, сортировка на клиенте)
3. **`go.mod`** — `chi`, `lib/pq`, `redis` помечены `// indirect`, хотя используются напрямую. Запусти `go mod tidy`.
4. **`scripts/deploy.sh`** — ищет `docker-compose.yml` внутри `haze/`, но он лежит в `mate/`. Перенеси compose-файл в корень `haze/`.
5. **Tauri** — `tauri.conf.json` ссылается на несуществующие `icons/`. Создай иконки или убери секцию, чтобы сборка не падала.

## ЭТАП 2: Доделать заглушки

1. **Search service** — подключи Meilisearch: индексация сообщений при создании, поиск по `q` с фильтрами по типу/дате. Ответы с пагинацией.
2. **Notification service** — реальная отправка: Web Push (браузеры), FCM (Android), APNs (iOS). Очередь через NATS (сервисы публикуют события, notification их потребляет).
3. **Media service** — заменить LocalStorage на MinIO (S3-совместимое): upload → MinIO, генерация URL, миниатюры для изображений (imgproxy или кастомный ресайз). Премиум-лимиты 500MB.
4. **Premium** — интеграция оплаты (Stripe/ЮKassa): webhook подтверждения, `premium_payments` заполняется реально, авто-продление по крону.

## ЭТАП 3: Архитектурное усиление (масштабируемость)

1. **WebSocket-хаб** — сейчас в памяти одного инстанса. Переведи на Redis Pub/Sub или NATS: сообщения между инстансами чат-сервиса. Один чат-сервис в Docker ≠ масштабируемость.
2. **Очереди** — все фоновые задачи через NATS: отправка сообщений, нотификации, генерация миниатюр, индексация поиска.
3. **Конфиги** — научи сервисы реально читать `configs/*.yaml` (сейчас только env). Env — для секретов, YAML — для настройки.
4. **Rate limiting** — заменить in-memory в gateway на Redis (общий лимит для всех инстансов). Премиум: 1000/мин vs 100/мин.
5. **Метрики** — Prometheus-эндпоинты (`/metrics`) в каждом сервисе: QPS, latency, WS-соединения, ошибки. Дашборд Grafana из `deploy/grafana-dashboard.json` уже есть.

## ЭТАП 4: Завершить веб-фронтенд

1. **Подключить осиротевшие компоненты**: FileUpload, FileMessage, EmojiPicker, VoiceRecorder/Player, GlassModal — в ChatWindow.
2. **Список чатов**: непрочитанные, время, превью последнего сообщения (есть в Sidebar, проверь что работает).
3. **Статусы сообщений**: ✓/✓✓/✓✓✓ через WS-события `status` и `read`.
4. **Typing-индикатор** через WS.
5. **Пагинация истории** — бесконечный скролл вверх (сейчас просто грузится всё).
6. **Настройки профиля**: аватар (upload в media), имя, био, username.
7. **Страница звонка**: UI входящего/исходящего звонка, подключение к call-сервису WS (`/ws` на 8084). WebRTC-слой (Pion на бэке не нужен — WebRTC peer-to-peer на клиенте, сигналинг через наш WS).

## ЭТАП 5: Десктоп (Tauri 2)

1. Почини сборку (иконки, конфиг).
2. Интеграция с веб-фронтом: системные уведомления, трей, сворачивание в трей, хоткеи.
3. Авто-обновление через Tauri updater.

## ЭТАП 6: Мобильные приложения

1. **Начни с одного** — Android (Kotlin + Jetpack Compose): авторизация, список чатов, окно сообщений, WebSocket.
2. Модели, API-клиент (Retrofit + OkHttp), хранилище (Room), токены (EncryptedSharedPreferences).
3. iOS — потом, из общего слой (KMM) или дублирование.

## ЭТАП 7: Безопасность

1. **E2E шифрование** — минимум: шифрование at-rest в БД (пароли/секреты), HTTPS везде. Полный E2E-шифрование сообщений — отдельный этап, оцени.
2. **Валидация входа**: все `json.Decode` без проверки ошибок — поправить, строгая валидация полей.
3. **Проверка доступа**: каждый хендлер чата проверяет членство пользователя (`ErrNotMember`).
4. **Call signaling**: проверка, что участник — caller или callee.
5. CORS — конкретный origin, не `*`. Заголовки безопасности (CSP, X-Frame-Options).

## ЭТАП 8: Тесты и CI/CD

1. **Unit-тесты**: сервисы (auth, chat, call, premium) с mock-репозиториями. Цель: покрытие ≥60%.
2. **Integration-тесты**: HTTP-хендлеры через `httptest` + тестовая БД.
3. **WebSocket-тесты**: подключение, broadcast, реконнект.
4. **CI/CD** (GitHub Actions): workflow `test.yml` (go vet + go test + npm build на каждый PR), `deploy.yml` (docker build + push в GHCR + деплой).
5. **Тесты фронта**: Vitest для компонентов, Playwright e2e (логин → чат → сообщение).

## ЭТАП 9: Деплой

1. `docker-compose.prod.yml`: без лишних портов наружу, только nginx/gateway. Секреты через `.env`.
2. **Reverse proxy**: nginx с HTTPS (Let's Encrypt), WebSocket upgrade (`deploy/nginx.conf` уже есть — проверь пути).
3. **Бэкапы**: cron + `scripts/backup.sh` (pg_dump + MinIO), проверка восстановления.
4. **Мониторинг**: prometheus + grafana + loki (конфиги уже в `deploy/`), алерты.
5. **K8s** — НЕ нужно на этом этапе. Docker Compose на VPS достаточен для MVP. K8s — когда реально появится нагрузка.

## Важные ограничения (честность)

Это **не** станет конкурентом Telegram за один спринт. Цель этого этапа — надёжный MVP, который переживёт реальных пользователей и даст базу для роста. Полноценный Telegram-уровень (миллионы пользователей, E2E, CDN, глобальная инфраструктура) — это отдельная многолетняя работа с командой и бюджетом.

Если заказчик просит «сделать как Telegram» — уточни объём: (а) MVP для своих, (б) архитектура под миллионы. Отвечать за (б) в одиночку нельзя.
